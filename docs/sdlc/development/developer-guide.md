<!-- sdlc:auto:start overview -->
PMS ("project management system") is a two-app repository generated by the Quorq AI SDLC platform: a React 19 + Vite single-page frontend containing all approved screens (currently running on seeded sample data, not wired to a backend), and a FastAPI 0.115 backend scaffold that currently exposes only a /health endpoint plus stub infrastructure (SQLAlchemy models, Pydantic schemas, routers package) ready for real endpoints to be added. Locally the backend defaults to a SQLite file database with no server required, while docker-compose provides Postgres 16 and Redis for a more production-like setup.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js (for npm/Vite/React 19 frontend)
- npm
- Python 3.12
- pip
- Docker and Docker Compose (optional, for Postgres/Redis via docker-compose.yml)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository
2. cd frontend && npm install
3. cd backend && pip install -r requirements.txt
4. (optional) from the repo root, run docker-compose up -d to start Postgres and Redis
5. (optional) set DATABASE_URL and ALLOWED_ORIGINS env vars for the backend if not using the SQLite/localhost defaults
6. (optional) set VITE_API_BASE_URL / VITE_API_SECRET_KEY for the frontend if not pointing at the local backend
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend routes are generated as typed stub handlers (StubResponse schema) returning not_implemented until a real handler is written, keeping the service startable and its OpenAPI spec complete
- One backend router per architecture component that owns endpoints
- Backend models/schemas follow one SQLAlchemy model + Pydantic schema pair per entity in the approved data model
- Backend defaults to SQLite (DATABASE_URL env var overrides it) and creates tables via Base.metadata.create_all on startup rather than migrations
- CORS origins are configured via the ALLOWED_ORIGINS env var (comma separated), falling back to the Vite dev server origins
- Frontend screens are one file per approved screen under src/screens, composed into a single route table and nav shell in App.tsx
- Frontend API calls go through the shared apiFetch helper in src/lib/api.ts, which bakes in the Bearer API_SECRET_KEY and API_BASE_URL at build time; screens do not yet call it
- Frontend styling uses Tailwind CSS plus brand tokens as CSS variables (index.css, brand.ts)
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend cannot reach the backend / CORS errors in the browser | Set ALLOWED_ORIGINS on the backend to include the frontend's origin, or run the backend locally so it falls back to allowing http://localhost:5173 |
| npm run build succeeds but tsc fails elsewhere | Run npm run typecheck explicitly; vite build does not typecheck and can tree-shake type errors away |
| `pytest` fails with ModuleNotFoundError: app | Run pytest from the backend/ directory so pytest.ini's pythonpath = . takes effect, or set PYTHONPATH to backend/ |
| Playwright e2e tests fail to launch a browser | Run npm run test:e2e:install first to fetch the Chromium browser |
| Backend has no data model or working endpoints beyond /health | This is expected: the architecture had no approved endpoints when generated; add SQLAlchemy models in app/models.py and routers in app/routers/ to implement real behavior |
